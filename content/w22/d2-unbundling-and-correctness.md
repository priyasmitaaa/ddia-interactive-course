:::problem A database is a bundle of features. Can we take it apart?
Inside one database you already have several **derived data structures** that the database keeps consistent for you: **secondary indexes**, **materialized views**, **replication logs**, and **full-text indexes** in some products. When you create an index, the database scans a consistent snapshot, builds the index, then keeps it up to date from subsequent writes. That's exactly what CDC plus a new consumer does across systems (Chapter 11). So a whole organization's data systems can be seen as one big database whose "indexes" live in different products.
:::

:::intuition Unbundled: storage, logs and derivation functions
**Unbundling the database** means building applications by composing specialized storage and processing systems, connected by **ordered logs** and **derivation functions** (stream processors), instead of relying on one product to do everything. Two ways to think of it:
- **Federated databases (unified reads)** offer one query interface over many backends. That's useful for reading, but it doesn't solve keeping them consistent.
- **Unbundled databases (unified writes)** make writes go to a log, from which every system is derived. This is the "**database inside-out**" idea, where the log is the primary interface and indexes and views are consumers.

**Designing around dataflow.** Treat application code as **derivation functions**: when an input changes, recompute the affected outputs. A spreadsheet is the familiar model. Change a cell, and every formula that depends on it updates. Stream processors and materialized views generalize this to many machines. Separating **state** (in durable storage) from **application logic** (stateless code consuming and producing streams) also clarifies who owns what.

**The read path and the write path.** Work can be done eagerly when data is written (precompute, materialize, push) or lazily when it's read (query on demand). Indexes, caches and materialized views move the boundary toward the write path. Querying raw data moves it toward the read path. Chapter 1's Twitter timelines are the classic example, and it's a trade-off you can tune per feature. Taken further, **clients can subscribe** to changes in derived state, so the push from server to browser or device becomes the end of the write path (Chapter 11's change streams reaching the UI).
:::

:::extra Aiming for correctness
- **The end-to-end argument.** A function can be implemented correctly only with knowledge held by the application at the endpoints, and lower layers can only make it more efficient. Example: TCP removes duplicate *packets*, and a stream processor may give exactly-once *processing*. But if a user's request is retried after a timeout, the database may still see the "transfer $11" request twice. Only an **end-to-end request ID**, generated by the client and carried all the way to the database where a uniqueness constraint enforces it, suppresses duplicates reliably. Lower-level guarantees don't compose into end-to-end correctness automatically.
- **Enforcing constraints with logs.** A uniqueness constraint ("one owner per username") can be enforced by routing all claims for a name to the same log partition and processing them sequentially: the first claim wins, as in Chapter 9's total order broadcast. Multi-partition requests, like a payment debiting one account and crediting another, can be split into stages with a unique request ID, each processed in its own partition, deterministically and idempotently. This gives correctness **without** atomic commit across partitions.
- **Timeliness vs integrity.** "Consistency" conflates two things. **Timeliness** means users see an up-to-date state; violations are temporary, and waiting fixes them. **Integrity** means no corruption or contradictory data, and nothing lost; violations are permanent and need explicit repair. In many applications integrity matters much more than timeliness. A bank can show a pending transaction late, but must never lose money. Log-based, asynchronous systems can provide strong integrity with weaker timeliness. Some constraints can even be **checked after the fact**, with compensation (apologize, refund), as Chapter 9 discussed.
- **Trust, but verify.** Hardware and software do corrupt data: bit flips, bugs, misconfiguration (Chapter 8's weak lying). Mature systems **audit** themselves. They check integrity with checksums, verify backups by restoring them, and compare derived data against its source. Event logs and deterministic derivation make that easier, because you can rerun and compare.
:::

:::details Worked example: end-to-end duplicate suppression
A mobile app submits "pay $50 to Bob". The request times out on a flaky network, and the app retries.
- **Without an end-to-end ID**: the server receives two identical requests. The database's transactions are perfect and the stream processor is exactly-once, yet Bob gets $100. Each layer did its job, and the failure is between the endpoints.
- **With an end-to-end ID**: the app generates `request_id = 7c9e…` once, before the first attempt, and resends the same ID on retry. The server writes the payment with a **unique constraint on request_id**, or appends it to a log partitioned by request ID and ignores duplicates. The second attempt is detected and returns the original result.

The pattern generalizes: idempotency keys in payment APIs, client-generated IDs in event-sourced commands, and Exercise 44's deduplication table.
:::

### explain
Explain how you could enforce "username must be unique" without a distributed transaction, using a log.
>>>
Partition a log of username claims by the username, for example by hash, so all claims for the same name land in the same partition, where they're totally ordered. A single-threaded processor per partition reads the claims in order and decides deterministically: the first claim for a free name succeeds and later ones fail. It records the decision, for example by appending an "accepted" or "rejected" event keyed by the client's request ID. Clients wait for the outcome event for their request ID. Every replica processing the log reaches the same decision, and the processor is deterministic and idempotent by request ID, so retries are safe, with no 2PC (Chapter 9's total order broadcast construction, generalized). It's linearizable per name, at the cost of the client waiting for the log round trip.
:::
