:::problem "The last five minutes" is ambiguous
Stream processors often deal with time, especially for analytics with windows like "last five minutes". That should be unambiguous, but it's "surprisingly tricky" (p. 452).

A **batch** process crunches through historical events quickly. If it breaks data down by time, it uses the **timestamp in each event**. The clock of the machine running the job is irrelevant, since a year of history may be processed in a few minutes and the timeline of interest is the year, not the minutes. Using event timestamps also makes the job **deterministic**: rerunning the same input gives the same result (Chapter 10) (pp. 452–453).

Many **stream** frameworks, by contrast, use the **local system clock of the processing machine**, the **processing time**, to decide windows. That's simple, and it's reasonable if the delay between an event's creation and its processing is negligible. It **breaks down when there's significant processing lag** (p. 453).
:::

:::intuition Event time vs processing time
**Why processing is delayed** (p. 453): network faults (Chapter 8), contention in the broker or processor, a **restart** of the consumer, or **reprocessing** past events while recovering from a fault or after fixing a bug.

**Message delays also reorder messages.** A user makes one request (handled by server A) and then another (server B). Both emit events, but B's reaches the broker first. Stream processors see B, then A, the opposite of what happened.

**The Star Wars analogy**: Episodes IV, V and VI came out in 1977, 1980 and 1983, Episodes I, II and III in 1999, 2002 and 2005, and VII in 2015. Watching in release order, your *processing* order is inconsistent with the *narrative* order. **The episode number is like the event timestamp, and the date you watched is the processing time.** Humans cope, but stream algorithms must be written specifically to handle such timing and ordering issues (p. 453).

**Confusing them produces bad data** (Figure 11-7). A processor measures requests per second. You redeploy it, it's down for a minute, and then it processes the backlog. Measured by processing time, there's a gap and then a sudden **anomalous spike**, although the real rate was steady (pp. 453–454).
:::

:::details Knowing when you're ready, and whose clock to use (pp. 454–456)
**Knowing when you're ready** (pp. 454–455). With **event-time** windows, you can never be sure you've received all events for a window. You've been counting events for minute 37, and now most arriving events are from minutes 38 and 39. When do you declare minute 37 finished and output its count? You can **time out** after seeing no new events for a while, but some events might still be buffered on another machine behind a network interruption and turn up later. You must handle **straggler events** that arrive after the window was declared complete. There are two options:
1. **Ignore the stragglers**. They're probably a small percentage in normal circumstances. **Track the number dropped as a metric**, and alert if it becomes significant.
2. **Publish a correction**: recalculate the window with the stragglers and publish the updated value, possibly retracting the previous output first.

Sometimes you can use a **low watermark**, "from now on there will be no more messages with a timestamp earlier than t", and have consumers wait for it before treating a window as ready. But if **timestamps are generated by clients**, you can't be sure there are no pending events somewhere, so stragglers older than the watermark are still possible.

**Whose clock are you using?** (p. 455). Events can be buffered at several points. A **mobile app** used offline buffers events and sends them when it next has a connection, hours or days later. To consumers they look like **extremely delayed stragglers**. The timestamp should really be when the user interaction happened, by the **device's** clock. But **user-controlled device clocks often can't be trusted**, being set wrong by accident or on purpose (Chapter 8). The server's receive time is more likely to be accurate, but less meaningful. One approach is to log **three timestamps**:
- when the event occurred, by the **device** clock;
- when it was **sent** to the server, by the **device** clock;
- when it was **received**, by the **server** clock.

The difference between the last two estimates the **offset** between device and server clocks, assuming network delay is negligible compared with the accuracy you need. Apply that offset to the first timestamp to estimate when the event really happened, assuming the offset didn't change between occurrence and sending.

This isn't unique to streams. **Batch processing suffers exactly the same issue**, but it's more noticeable in streaming, where we're more aware of time passing (p. 456).
:::

### explain
Explain the three-timestamp technique for events from mobile devices, its assumptions, and what it buys you.
>>>
Record (1) the time the event occurred, by the device clock, (2) the time it was sent to the server, by the device clock, and (3) the time it was received, by the server clock. Assuming network delay is small relative to the required accuracy, (3) minus (2) estimates the device clock's offset from the server clock. Adding that offset to (1) estimates the true time of the event in server-clock terms, assuming the offset didn't change between occurrence and sending (p. 455). That gives meaningful event timestamps (when the user actually acted, even if the event arrives days later) while correcting device clocks that are wrong by accident or on purpose. It doesn't make the event any less late. Late events still need straggler handling.
:::
